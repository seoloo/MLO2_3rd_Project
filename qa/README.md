# 티켓가드 자동화 QA

> **처음 쓰는 팀원이라면 [설치·사용 안내](docs/install-and-use.md)부터 보세요.** 설치 방법 고르기, 첫 시험, 결과 읽는 법, 내 API 시험하기, 문제 해결까지 순서대로 정리했어요.

티켓가드(실시간 매크로 탐지 예매 시스템)가 **사람과 봇을 정확하게 판정하고, 행동 이벤트를 빠짐없이 처리하고, 멈췄다가도 회복하는지**를 자동으로 확인하는 QA 도구입니다. 사람인지 봇인지 정답을 아는 세션과 이벤트를 파일에 적어 두면, 프로그램이 입력을 시험 대상에 넣고 돌아온 결과를 정답과 비교해 채점하고 보고서로 남깁니다.

> 2026-11-02에 주제를 정보지킴(스미싱 판정)에서 티켓가드로 바꿨습니다. 채점 엔진·보고서·데스크탑 앱 구조는 그대로 두고, 시험 사례·판정 값·연결 형식·가짜 서버를 티켓가드 [연결 계약](../docs/contract.md)에 맞게 바꿨습니다. 같은 날 이 README를 **안내판**으로 줄이고 자세한 내용은 주제별 문서로 나눴습니다. 무엇이 언제 왜 바뀌었는지는 [변경 기록](docs/changes.md)에 있습니다.

## QA 지도

QA는 **만드는 쪽**(정답을 아는 입력)과 **채점하는 쪽**(결과를 정답과 비교)으로 나뉩니다. 그 사이의 **시험 대상**은 다른 팀원이 만들고, QA는 그 자리에 가짜를 끼워 먼저 연습합니다.

```
 만드는 쪽 (QA)                       시험 대상 (다른 팀원)                     채점하는 쪽 (QA)
 ─────────────                        ────────────────────                     ──────────────
 시험 사례  cases/        ──입력──▶   판정 API · 파이프라인   ──결과──▶       QA 러너 (콘솔 · 데스크탑 앱)
 매크로 봇  bots/         ──트래픽─▶   Django 예매 사이트                       └▶ 보고서 · 대시보드 · CI
                                       (아직 없으면 가짜로 대신)
 정답(사람인지 봇인지)은 시험 대상에 보내지 않고 채점하는 쪽에만 넘깁니다.
```

| 구성 요소 | 어느 쪽 | 언어 · 위치 | 하는 일 | 상태 | 자세히 |
|---|---|---|---|---|---|
| 시험 사례 | 만드는 쪽 | JSON · `cases/` | 정답을 아는 세션(사람·봇 A~D 7개)과 파이프라인 시나리오(5개) | 완료 | [시험 케이스 작성법](docs/test-cases.md) |
| 매크로 봇 | 만드는 쪽 | Python · `bots/` | 정답을 아는 트래픽을 Django 예매 사이트에 실제로 보내고 정답 표를 QA 쪽에 남김 | 진행 중 (설계 완료) | [매크로 봇 작업 계획](bots/README.md) |
| QA 러너 (콘솔) | 채점하는 쪽 | C# · `src/QaRunner` | 입력을 넣고 결과를 정답과 비교해 보고서로 남김 | 연습용 대상으로 완료, 실제 연결 대기 | [콘솔 프로그램](docs/console.md) · [시험 흐름과 기준](docs/tests.md) |
| 데스크탑 앱 | 채점하는 쪽 | C# WPF · `src/QaRunner.Desktop` | 같은 채점을 화면에서 버튼으로 | 완료 | [데스크탑 앱](docs/desktop-app.md) |
| 가짜 예매·판정 서버 | 시험 대상 대역 | C# · `src/QaRunner/AppMock` | 백엔드가 없을 때 앱이 대신 붙어 요청 형식을 채점받는 서버 | 완료 (앱 연결 대기) | [가짜 예매·판정 서버](docs/mock-server.md) |
| 연습용 판정기 · 가짜 파이프라인 | 시험 대상 대역 | C# · `Verdicts/`, `Pipeline/` | 실제 판정 API·파이프라인 대신 일부러 틀리게 만든 대상. 채점기가 틀린 결과를 잡는지 확인 | 완료 | [시험 흐름과 기준](docs/tests.md) |
| 보고서 · 대시보드 · CI | 결과 | C# · `Reports/`, `.github/` | 실행별 HTML·JSON 보고서, 추이 대시보드, 푸시마다 자동 검사 | 완료 | [보고서·대시보드와 자동 검사](docs/reports-ci.md) |
| 팀 공유 · AI 사례 | 뼈대 | C# · `QaRunner.Sharing.Api`, `Collaboration/` | 실행 기록 공유, Runpod 새 유형 봇 사례 생성 자리 | 스켈레톤 | [연결 스켈레톤 안내](docs/collaboration-skeleton.md) |

| 시험 대상 (QA가 만들지 않음) | 누가 | 지금 |
|---|---|---|
| Django 예매 사이트 | 프론트 (`codex/frontend`) | 있음. 회원·좌석·예매와 행동 이벤트 수집만 하고 판정은 하지 않음. 매크로 봇의 대상 |
| 판정 API (FastAPI) | B | 아직 없음 → 연습용 판정기로 대신. 생기면 `--api-url`로 붙임 |
| Kafka · Spark · MongoDB 파이프라인 | B · C | 아직 없음 → 가짜 파이프라인으로 대신. 생기면 `--kafka`·`--mongo`로 붙임 |

## 기획과 지금이 다른 점

문서 곳곳의 말이 기획서 기준으로 쓰여 있어서, 지금 실제와 다른 곳이 있습니다. 헷갈리면 이 표를 먼저 봅니다.

| 항목 | 기획서 | 지금 | QA 문서를 읽을 때 |
|---|---|---|---|
| 예매 화면 | React Native · Expo 앱 (A) | Django 예매 사이트 (`codex/frontend`, 임시 대상) | "앱"·"앱 영역"은 RN 앱 기준으로 쓴 말입니다. 매크로 봇의 대상은 Django 사이트입니다 |
| 예매·수집·판정 API | FastAPI (B) | 아직 없음. Django가 예매와 행동 이벤트 수집(`/api/events/`)만 함 | 판정 시험은 연습용 판정기로 돌고, 실제 API에 붙일 코드(`--api-url`)만 준비되어 있습니다 |
| 가짜 예매 서버 (WBS 4.2) | QA가 프론트에 내주는 가짜 서버 | C# 가짜 예매·판정 서버(`mockapi`)가 있음. Django 사이트가 먼저 생겨 역할이 겹침 | 연결 계약 v0 형식 검사용으로 둘지 팀이 정합니다 |
| 트래픽 생성 | 2주 차 Locust · Playwright | 1주 차에 `qa/bots/`로 시작, 대상은 Django 사이트 | [매크로 봇 작업 계획](bots/README.md) |
| 데이터 파이프라인 | Kafka → Spark → MongoDB | 아직 없음 | 가짜 파이프라인으로 채점기·측정 코드만 확인합니다 |

헷갈리기 쉬운 것:

- **포트 8000이 겹칩니다.** 가짜 예매·판정 서버의 기본 포트와 Django 사이트가 모두 8000입니다. 함께 켜려면 가짜 서버를 `--port 8010`처럼 다른 포트로 엽니다.
- **연습용 대상은 일부러 틀립니다.** 연습용 대상으로 돌릴 때 나오는 실패는 채점기가 틀린 결과를 잡아내는지 보려는 것이라 정상입니다.
- **시험 사례와 매크로 봇은 다릅니다.** 시험 사례(`cases/`)는 손으로 쓴 대표 예시로 채점기를 확인하는 용도이고, 매크로 봇은 실제 사이트에 수백~수천 세션을 보내 판정 쪽이 학습·평가에 쓸 데이터를 만듭니다.
- **문서 안의 경로는 `qa/` 폴더 기준입니다.** 예: `src/QaRunner`는 `qa/src/QaRunner`입니다.

## 한눈에 보기


| 질문 | 답 |
|---|---|
| **왜 만드나** | 기획서의 핵심인 "결제 전에 몇 초 안에 판정하고, 데이터 처리가 정확하다"를 숫자로 증명하기 위해서입니다. 정답을 아는 봇·사람 세션, 중복 3회·역순·30초 지연·초당 5건 × 5분·Spark 30초 중단 같은 조건은 사람이 손으로 정확히 재현할 수 없고, 코드를 고칠 때마다 다시 확인해야 합니다. |
| **어떻게 하나** | ① 입력을 넣고 → ② 정답을 따로 계산하고 → ③ 시스템이 낸 실제 값을 꺼내 → ④ 비교해서 보고서로 남깁니다. 정답(사람인지 봇인지)은 시스템에 보내지 않고 QA 안에만 두므로, 시스템이 틀려도 정답은 오염되지 않습니다. |
| **무엇이 남나** | 실행 번호별 HTML·JSON 보고서, 통과율·p95·회복 시간 추이 대시보드, CI의 ✔/✘, 종료 코드(0 통과, 1 실패, 2 준비 오류) |
| **왜 C#인가** | HTTP·Kafka·MongoDB·JSON을 공식 라이브러리로 바로 쓸 수 있고, Python으로 만든 시스템과 언어가 달라 정답 계산이 자연스럽게 분리됩니다. 부하가 초당 5건 수준이라 C++의 속도는 필요하지 않습니다. |

시험은 무엇을 점검하는지에 따라 세 영역으로 나뉩니다. 보고서·대시보드·데스크탑 앱 모두 이 영역으로 묶어 보여 줍니다.

| 영역 | 시험 | 넣는 것 | 비교하는 것 |
|---|---|---|---|
| **서비스** | 판정 시험 (`verdict`) | 사람·봇 세션의 행동 (대기열 진입·좌석 클릭·점유·결제) | 판정 묶음 (사람은 정상·관찰, 봇은 추가 확인·보류), 봇 탐지율·사람 오탐률 |
| | 파이프라인 시험 (`pipeline`) | 행동 이벤트 + 중복·역순·지연 조건 | Bronze 보관 건수, Silver 고유 건수, 격리 건수, Gold 60초 구간 집계 |
| | 부하 시험 (`load`) | 세션 판정 요청 동시 반복 + 이벤트를 초당 N건씩 계속 | 판정까지 걸린 시간 p95(API 응답 시간 p95), 오류율, Gold 반영 시간 p95, 적체 |
| | 복구 시험 (`recovery`) | 이벤트를 계속 보내면서 처리를 멈췄다 재가동 | 재가동 후 회복 시간, 최종 집계 일치 |
| **앱** | 가짜 예매·판정 서버 (`mockapi`) | 앱이 백엔드 대신 이 서버에 보낸 예매·이벤트 요청. 서버는 추가 확인·보류·매진·판정 지연·오류 등을 골라 돌려줌 | 요청이 계약 3~5장 형식(경로·방식·JSON 필드)과 같은지. 추가 확인·오류 화면은 A가 앱에서 확인 |
| **QA 도구** | QA 도구 점검 (`selfcheck`) | 답을 이미 아는 입력 12가지 (코드에 고정) | 채점기가 틀린 결과를 잡아내는지, 정답 계산·p95·탐지율·보고서 저장이 맞는지 |

## 진행 상황


| 단계 | 내용 | 상태 |
|---|---|---|
| ① 스켈레톤 | 사례 파일 → 연습용 판정기 → 채점 → 콘솔 출력·종료 코드 | 완료 |
| ② 결과 저장·HTML 보고서 | 실행 번호별 JSON·HTML 보고서 저장 | 완료 |
| ③ 실제 API 연결 | 계약 초안대로 수집 API로 세션 행동을 보내고 판정 조회 API를 읽는 코드 완료 (`--api-url`). B의 백엔드가 나오면 실제로 확인 | 연결 대기 |
| ④ 파이프라인 시험 | 가짜 파이프라인으로 동작 확인. Kafka 발행·MongoDB 읽기 코드 완료 (`--kafka`, `--mongo`) | 연결 대기 |
| ⑤ 부하·복구 시험 | 가짜 파이프라인으로 동작 확인. Spark 컨테이너 중단·재가동 코드 완료 (`--spark-container`) | 연결 대기 |
| ⑥ 자동 실행·CI | GitHub Actions에서 푸시마다 빌드·테스트·시험 실행. docker-compose 서비스는 인프라가 생긴 뒤 | 일부 완료 |
| ⑦ 실행 기록 대시보드 | 실행할 때마다 `reports/dashboard.html`을 다시 만들어 추이를 표시 | 완료 |
| 데스크탑 앱 | 홈·여정 안내·조건 시트·결과·기록·관리 화면을 갖춘 Windows 앱 | 완료 |
| 시험 영역 | 서비스 · 앱 · QA 도구로 시험을 묶음. QA 도구 점검 12가지, CI에서 항상 통과해야 함 | 완료 |
| 티켓가드 전환 | 세션 사례(사람·봇 A~D), 판정 네 단계와 묶음 채점, 탐지율·오탐률, 행동 이벤트 형식, `ticket-events`·`ticketguard` 기본값 | 완료 (2026-11-02) |
| 앱 영역 ① 가짜 예매·판정 서버 | 예매·수집·판정 조회 API를 흉내 내는 서버(응답 방식 16가지)와 요청 계약 채점. 데스크탑 앱 홈 › 앱 카드, 콘솔 `--suite mockapi` | 완료 (A의 앱 연결 대기) |
| 매크로 봇 (트래픽 생성기) | Locust(가상 사람·봇 A·B·D)·Playwright(봇 C)로 프론트의 Django 예매 사이트에 실제 트래픽을 보내고 정답 표를 QA 쪽에 남김. 작업 방법은 [매크로 봇 작업 계획](bots/README.md) | 진행 중 (설계 완료, 2026-11-02 구현 시작) |
| 탐지 평가 | 재생 시험(S3 기록을 원래 속도로 다시 흘림)·새 유형 봇 평가·사람 테스트 표본 관리 (기획서 4.6·4.7) | 계획 (3~4주 차 이후) |
| 앱 영역 ②③ | 앱 계약 시험(Jest 결과 수집), 화면 흐름 시험(Maestro 등) | 계획 |
| AI 사례·팀 공유 | 예제 세션 → 채점 → 로컬 보고서 → 공유 API → 팀 기록 조회 뼈대. Runpod(새 유형 봇 시나리오)·EC2 연결 전 | 스켈레톤 |

- **연결 대기:** ③④⑤는 연습용 대상으로 다 돌아가고, 실제 시스템에 붙이는 코드도 준비되어 있습니다. 팀원 작업이 나오면 옵션(`--api-url`, `--kafka`, `--mongo`)만 넣어 확인합니다.
- **구조:** 채점기·정답 계산기·보고서는 바뀌지 않고, 시험 대상만 가짜에서 실제로 바꿔 끼웁니다.

## 빠른 실행

명령은 모두 `qa/` 폴더에서 실행합니다. .NET 10 SDK가 필요합니다 ([콘솔 프로그램](docs/console.md#설치)).

```bash
dotnet run --project src/QaRunner.Desktop
```

```bash
dotnet run --project src/QaRunner -- --suite selfcheck
```

```bash
dotnet test
```

코드·옵션·파일·화면이 바뀌면 해당 문서와 이 README의 [진행 상황](#진행-상황)을 같은 커밋에서 고치고, 바뀐 방향이 크면 [변경 기록](docs/changes.md)에 한 줄 남깁니다.
